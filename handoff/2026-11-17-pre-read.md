# 17 November 2026: a Jev pre-read of local bulk, measured, not in the map

**Why.** The owner wanted Jev to pre-read local bulk (logs, CI and test output, long files,
other chats' transcripts) so that only the relevant part is opened, as web batch does for web
pages. The owner said yes on 17 November 2026 to sending that local text to TypeSafe, in all
projects; customer data and a product's live records are another question.

**Result.** The script works and missed its bar on two of four points, so the map has no row
for it. Big local output stays with context-mode.

## What changed

- `plugins/cookbook/skills/cookbook/scripts/pre-read.mjs` (new): a sibling of
  `web-batch.mjs`, not a files input to it. Web batch gives one row per page and plans
  Firecrawl credits; here a row is a part of a file, there is no search or scrape, and private
  folders are checked first. It uses web batch's splitter, thresholds (0.7 and 0.3) and Jev
  caller.
- Two Nouls per part, with their own wording per kind (log, file, chat transcript): does the
  part contain what the question asks for, and is it about the subject. Verdicts: `answers`,
  `uncertain`, `related` (on the subject, no answer: listed in a footer, not opened),
  `doesn't`, `error`.
- Private folders: a port of the pure functions in the compaction plugin's `atlas-scope.ts`
  (0.4.1). The list is the plugin's `privateRoots` in the user settings (`pluginConfigs`), plus
  `--private-roots` and the plugin's private-session markers. A list that cannot be read
  sends nothing.
- No text on disk: the manifest, the cache and the worker's job file hold line ranges, hashes
  and probabilities. The worker reads each part from the source file again and refuses a part
  whose hash changed. A test writes marker words into a file and searches every written file.
- `web-batch.mjs`: `chunkText` takes its cap as a second argument, `readJevAnswers` takes the
  question ids, and six helpers are exported. Its behaviour and its 18 tests are unchanged.
- `recipes/pre-read.md` (new), linked from `recipes/web-batch-measure.md`. `SKILL.md` and
  `catalog.json` are unchanged.

## The measurement (17 November 2026, jev-1.14.0)

The bar was written in the chat before the first call and is `BAR` in the script.

| Point | Bar | Measured | |
| --- | --- | --- | --- |
| Recall of the relevant parts | at least 90 %, no question with all of its own missed | 21 of 21 | met |
| `answers` rows that are not relevant | at most 10 % | 13 of 31 (42 %) | missed |
| Share of the text in the parts to open | at most 35 % | 46 % | missed |
| Recall against a keyword rule opening as many parts | higher | 21 of 21 against 17 of 21 | met |

- The set: two failed CI runs of this repository (their three job logs joined, 9 and 5
  parts), the closed `HANDOFF.md` (16 parts) and two chat transcripts of this project (10 and
  14 parts as rendered text). Eleven questions, 124 part-and-question labels, 21 relevant.
- The labels: five `cookbook:reader` agents, one per source, each given only a copy of the
  parts and the questions, before any judged run. Every agent reported reading every page.
  The copies were in the session's scratchpad and are gone.
- 34 of the 55 opened parts were not relevant: 13 as `answers`, 21 as `uncertain`. The handoff
  file is the worst (21 of its 29 opened parts), the logs and one chat the best. No call
  failed. 518,083 Jev input tokens in 124 requests, plus one one-part call to prove the pipe.
- The labels were not looked at again after the judged runs, and no wording was changed.

## The review before the pull request was marked ready

A `cookbook:review` agent that did not build the change read the first commit (`3c5a4b5`) and
reproduced four ways a private source could still reach the judge. All are fixed in the next
commit, each with a test. No private folder is set on this PC and none of the five measured
sources was a marked chat, so the measured runs sent nothing they should not have.

- High: the "text names a private folder" check read the raw file only. A folder inside a JSON
  string (after an escaped line end) or split by colour codes in a log was missed. Now the raw
  text, every part as it would be sent and every string of a JSON line are checked.
- Medium: a chat read as another kind (`--kind file`, a copy named `.txt`, a byte order mark)
  skipped the "ran in or above" check. Now every JSON line's working folder counts.
- Medium: the judge stage did not ask again. Now it reads the list again and checks the text
  it has just read; with no list it sends nothing.
- Medium: a subagent's chat of a marked session was not matched. Now the folders of the path
  and the session ids in the lines are matched against the markers.
- Low, fixed: the path as typed is checked beside the real one; an unreadable settings file
  is reported in fixed words (the parser's message quotes the file); the Jev API's error text
  is cut to its status; a label for a part the run does not hold counts as a miss; the
  keyword rule fills up to the number Jev opened; a blank part after a full one is dropped; a
  forced kind that does not fit is an error; a UTF-16 log is read; "no question loses every
  relevant part" is in the score (`someFound_met`).
- The runs were scored again with the corrected keyword rule, without a new call: still 17 of
  21, since the rule had already opened as many parts as Jev in every run.
- Not covered, by decision: a private-folder list in managed settings or in a `--settings`
  file is not read (this PC has neither), and a `subst` drive letter that points into a
  private folder is not resolved.

## Outstanding

- **A second design** (owner: Claude, a new chat). What clears it: a new measurement on new
  labels that meets the same bar. TypeSafe's line-search cookbook asks one Choice over the
  lines of a part beside a Noul, so a row would name a few lines and not a whole part. The 124
  labels above are used up for tuning.
- The organisation's Jev rate limit was not read; no call was rate limited in 125 requests.
- **The launcher test that failed once under load** (owner: Claude, its own job). Reason: not
  looked into here; the test reads its child's output as JSON and got none. What clears it:
  the test tells a slow child from a failed one, or the failure is seen again and traced.

## Dead ends

- A files input beside `--urls-file` in `web-batch.mjs`: not built. The row model (a page's
  best part) and the credit stages do not fit a file's parts.
- An "is it real content" or "does it address an AI" Noul for local text: not asked. A chat
  with an assistant addresses an AI throughout, and neither answer would change a row.
